# Write-up 01: The token cost of a coordinated agent colony, measured against a single session

*Kevin Wilkins, November 2026. Every number below comes from [`measurements/MEASUREMENTS.md`](../measurements/MEASUREMENTS.md),
which is generated by a script from the run records. The plans, hypotheses and decision rules for each phase were
committed before that phase's first run: [`PHASE6.md`](../measurements/method/PHASE6.md),
[`PHASE7.md`](../measurements/method/PHASE7.md), [`PHASE8.md`](../measurements/method/PHASE8.md).*

**Summary.** A colony of agents coordinating through shared files consumed 7.7 times the tokens of one plain session
and reached the same score. Reducing the colony's coordination overhead brought its cost to approximately that of one
session, but not below it. The result supports a general practice for multi-agent systems: measure them against a
single agent working alone, and fix the criterion for success before the first run.

## Hypothesis

The design apiary started from (a textbook on stigmergic agent colonies) holds that a colony of agents coordinating
through shared files, working in parallel lanes, outperforms a single agent on speed and cost. That design was
implemented as written, the threshold for "clearly better" was recorded in advance, and the design was measured
against it.

## Results

Median total tokens per build (input, cache and output), three runs per arm, Claude Opus, one Windows machine. Every
build was graded by hidden tests that the agents did not see.

| Project | Plain session (one agent, no colony) | Colony as the textbook describes it (every task to a Forager subagent, several at once when ready) | Colony after the redesign (solo Queen, `create_plan`) |
|---|---|---|---|
| Small game, 8 modules, 38 hidden tests | **0.93M** tokens, 4.1 min, 38/38 | **7.19M** tokens (7.7x), 13.1 min, 38/38 | **0.90M** tokens (comparable to plain; 1.1x Phase 7's own plain runs), 4.0 min, 38/38 |
| Spreadsheet engine, 317 hidden tests | **3.09M** tokens, 13.6 min, 316/317 | **9.34M** tokens (3.0x), 22.9 min, 316/317 | **4.62M** tokens (1.5x), 13.5 min, 316/317 |

- **Before the redesign.** On the small project, the textbook colony used 7.7 times the tokens and 3.2 times the time
  of a plain session, for the same score. The pre-registered verdict was "parallel shows no clear saving over plain".
  Parallel lanes also did not outperform one Forager at a time (7.19M against 5.43M).
- **After the redesign.** With its planning overhead reduced, the same colony used **87% fewer tokens** than before
  (7.19M to 0.90M) and finished 3.3 times faster (13.1 to 4.0 minutes), with no loss of score. This placed it at
  approximately the cost of a plain session. It did not outperform plain: the pre-registered verdict for solo against
  plain was "no clear saving".
- **On the larger project**, no arm achieved higher quality. Plain, solo and foragers all scored a median of 316 of
  317. The colony cost 1.5 times (solo) to 3.0 times (foragers) the tokens of a plain session.

The hypothesis is therefore not supported. On neither project did a colony make building cheaper or better. The
redesign reduced the colony's overhead; it did not produce a saving.

## Changes made by the redesign

The changes follow from the transcripts of the Phase 6 runs:

1. **Planning was conducted as a conversation rather than a single call.** The Queen created tasks one at a time and
   re-read the ledger between them. `create_plan` accepts the whole plan in one call and refuses all of it if any task
   is invalid (overlapping write sets, unknown dependencies, a cycle).
2. **Each Forager carried a fixed start-up cost.** Each subagent began with 55k to 60k tokens of context (Claude Code's
   full system prompt, every tool, and the project's CLAUDE.md, which also loads the Queen's protocol), and re-read it
   on every call. About a quarter of Forager calls performed only colony bookkeeping.
3. **Solo mode.** When a plan contains no work that can run concurrently, the Queen performs the tasks itself (claim,
   work, close) rather than starting a Forager for each task.

A Phase 9 follow-up (a dedicated Forager agent with a short protocol and only the tools it needs) reduced a Forager's
first-call context from 55k to 60k tokens to about 14k in one probe run. **That probe is not counted**: the Phase 9
runs that would measure it have not been carried out, and no claim is made about it.

## What the colony provides in place of a saving

The colony is retained for properties that a plain session does not have:

- **Every claim, refusal and close is recorded as a line in an append-only ledger.** The record shows which agent did
  what, and what was refused and why. A plain session leaves, at most, a transcript.
- **A task closes only when its own check passes**, and the check is pinned by a hash at claim time, so an agent cannot
  rewrite it into one that passes (spec P-18; in a review of version 0.1.0, an agent did exactly that and the close
  succeeded).
- **A guard hook prevents agents from editing the colony's files directly.** See [write-up 03](03-guard-bypass.md).
- **Work stops for the human where the plan requires it.**

Whether these properties justify their cost to a team has **not been measured**. The runs establish the price (1.1 to
1.5 times plain, as shipped), not the value.

## Limits

- Two projects, both **exactly specified**. A single session built both almost perfectly, which left little room for
  any arm to score higher. Less precisely specified or substantially larger work is untested; a colony may yet show
  value there.
- One machine (Windows 10), one model, three runs per arm.
- Output tokens are a lower bound for colony runs (some calls are logged before their reply completes). The effect on
  total tokens is under 0.3%.
- Three hidden tests in the spreadsheet benchmark were corrected or removed after runs began, under a rule recorded in
  `PHASE8.md` before it was applied. The specification the agents built from did not change.
- The raw run records contain private paths and are not included in this repository. Each run's numbers are in the
  "Every run" table of `MEASUREMENTS.md`; the benchmark specifications and hidden tests are in [`bench/`](../bench/).

## Reproduction

Any build of either benchmark can be graded with the same hidden tests. Build `bench/skirmish/SPEC.md` (or
`bench/tally/SPEC.md`) in a separate folder, with any agent setup, and keep the hidden tests out of that folder. Then:

```bash
python -m pip install pytest
SKIRMISH_IMPL=<your build folder> python -m pytest -q bench/skirmish/hidden/tests   # 38 tests
TALLY_IMPL=<your build folder> python -m pytest -q bench/tally/hidden/tests         # 317 tests
```

`bench/*/hidden/reference/` contains a build that passes every test. Token counts were read from Claude Code's own
transcripts by `apiary/measure.py`.
